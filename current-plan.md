# Setauket — current plan

_Last updated: 2026-10-02, after the bulk consented import, the Qwen2.5-0.5B summarizer swap, a production embed-worker incident, and the split from Clothesline._

## Goal and boundaries

Build a local, cross-harness memory service that lets coding agents recall past work and preserve explicit decisions and preferences. Keep one source of truth in Setauket; integrations should submit visible turns or call existing tools, not implement their own memory system. Agent-to-agent messaging is **not** in scope here — that is [Clothesline](https://github.com/kplawver/clothesline).

- Python/Starlette serves the browser and Streamable HTTP MCP from one process. SQLite provides durable storage, FTS5 keyword search, and `sqlite-vec` search with local embeddings. A local `llama-cli` model summarizes inactive sessions.
- Bind only to loopback (default `127.0.0.1:19005`); no authentication or remote service. Install and run as a Homebrew user service.
- Connecting an MCP client **does not** capture a conversation. Turn submission is explicit unless a user enables a harness integration for an exact project path.
- Importers and live-capture integrations select visible user/assistant text and exclude structured reasoning, tool calls and results, system prompts, and images. MCP clients that submit turns themselves must apply the same filtering. Visible text can still contain secrets: capture is not a secret scanner.
- Keep raw submitted turns for three days after inactivity, then summarize and remove the raw turns atomically. Preserve attributed decisions and preferences until superseded. Do not automatically promote summaries into durable preferences.

## Shipped and verified

**v0.7.1** is the current release. **v0.7.0** split the combined 0.6.x service into this repository (memory, port 19005) and [kplawver/clothesline](https://github.com/kplawver/clothesline) (messaging, port 19004). Both suites are green (46 here, 18 there) with Ruff clean, and all four CI jobs pass on both repositories including Intel macOS.

v0.7.1 exists only to make the lockfile installable on Intel: onnxruntime has shipped no macOS x86_64 wheel since 1.23.2, so `brew install setauket` could not build an environment there. The lockfile now resolves against macOS x86_64, pinning onnxruntime 1.23.2 for that platform only. `requires-python` is capped below 3.14 because fastembed requires onnxruntime>=1.24.2 from 3.14 on. Nothing changed for Apple Silicon. Clothesline stayed at v0.7.0: its only post-release change was its own CI workflow, which the formula does not install.

- **Core memory:** attributed harnesses, agents, sessions, explicit turn submission, versioned decisions/preferences, keyword and semantic search, browser views, local embeddings and archive jobs, backup and index-rebuild commands.
- **Split from Clothesline (v0.7.0).** Sessions, turns, memories, embeddings, the archive worker, all session importers, and both capture integrations moved here; the message bus stayed in Clothesline. Identity is duplicated in both databases: the same `(installation_key, external_id)` resolves to the same logical agent within each service, but row IDs are not comparable across them. The old schema-v5 database was split with `scripts/split_legacy_db.py`, which preserved all 26,581 turns / 39,216 chunks / 488 sessions / 490 agents / 36 projects in Setauket and the single conversation plus its message in Clothesline, with identical IDs on both sides. Setauket's schema restarts at `user_version=1`.
- **MCP clients:** Claude Code, Zed, and **Oh My Pi (OMP)** have called Setauket tools. OMP has native HTTP MCP; it is not the separate Pi CLI.
- **Manual, opt-in import:** one saved session at a time from OMP, Pi, Claude Code, Codex, Zed, or OpenCode. Imports use Setauket's shared turn storage, have source checkpoints, and refuse changed history rather than merging it silently. Real saved sessions from all five newer readers were **dry-run only**; actual import writes were tested with synthetic fixtures. Zed/OpenCode SQLite sources are opened read-only.
- **Opt-in live capture:** a Claude Code plugin (MCP connection, memory skill, and prompt/Stop hooks) and an OMP extension/skill package. Each has its own exact-project allowlist; merely installing the integration does not enable capture. Both captured harmless real turns into **isolated** databases. OMP interactive input was also tested with a simulated extension event. Neither integration is installed/enabled globally as part of the release work, and no private saved history was imported into the production database.

## Validation progress (2026-10-02)

- **Backup/restore drill passed.** A fresh `setauket backup` of the live v5 database was restored into an isolated data directory (`.restore-drill/restored-data`, gitignored, models symlinked read-only) and verified at every layer: integrity ok, version gate/migrations idempotent via `Store`, row counts identical to the snapshot, keyword search, semantic recall with the real embedding model (paraphrase hit on the Zed test turn), browser pages 200, and MCP `tools/list` + `search_sessions` over HTTP on port 19005 with `semantic_available: true`. The original database was only read through the documented backup command and stayed healthy throughout. Encoded as a repeatable regression test in `tests/test_backup_restore.py` (CLI backup path, counts, integrity, recall, bus history, doctor/status on the restored copy).
- **CI added.** `.github/workflows/ci.yml` runs the uv-locked suite (pytest + ruff + `uv build`) on Ubuntu and macOS, plus a best-effort `macos-15-intel` x86_64 job (continue-on-error until real Intel validation), `claude plugin validate --strict` for the marketplace and plugin manifests, and a Bun syntax check for the OMP TypeScript extension. Added locally; not yet observed green on GitHub.
- **Summary quality groundwork (real model, synthetic sessions).** Qwen3-1.7B-Q8_0 via llama-cli, scripts in `.restore-drill/summary_eval{,2,3,4}.py`. Realistic ~5k-char sessions: fast (~3 s), faithful, no invented content (canary check), but lossy — a planted demo date and filenames were dropped. Long/repetitive content (~19–44k chars): degenerates — map/combine summaries echo log lines, the fixed `-n 800` output cap truncates tail facts, and the final combine can continue the echo mid-list. Greedy decoding (`--temp 0 --top-k 1`) did not change the degenerate behavior. Decision needed before trusting archival summaries of real coding sessions: larger summarizer (e.g. Qwen3-4B), raised `-n`, pre-dedup of low-signal lines, or accepting lossy summaries. Evaluation on reviewed real sessions still needs consent.

## Production incident (2026-10-02): stale Python after brew upgrade

The live service had run since Sep 30 from `python@3.12/3.12.14`; a brew upgrade later that day replaced it with 3.12.15 and deleted the old tree. The running process's stdlib paths dangled, so lazy imports inside the embed chain failed (`No module named 'gzip'`) and every embed job failed with backoff — discovered because freshly imported chunks had `embedded: 0`. A `brew services restart` fixed it (fresh process on 3.12.15; jobs retried and succeeded; `semantic_available` restored). Consider a doctor check that compares the running interpreter path against the venv's `pyvenv.cfg` home to catch this class of failure early.

Because archival permanently replaces raw turns with summaries, and 450 archive jobs would have run on restart with the old Qwen3-1.7B model, the archive jobs were deferred to 2026-10-16 and a unique index `jobs(kind, source_id)` was added to the live database so the daily sweep's `INSERT OR IGNORE` cannot re-queue them early. Release the 0.5B summarizer (or consciously keep 1.7B) before then; reset with `UPDATE jobs SET next_at=strftime('%s','now') WHERE kind='archive'` to run them now. Note the schema addition is local-only; a future migration could adopt the index properly.

## Possible follow-on integrations (not yet committed)

- Add live capture to other harnesses only after checking their actual event/hook APIs and consent controls. The separate Pi CLI has no built-in MCP client in the version inspected; an adapter is optional. Manual import remains the fallback.
  - Ideally, we can build a single plugin that conforms to the .agents standard that _most_ coding harnesses can use.
- Improve harness-side message-bus ergonomics: presence, heartbeat, and inbox delivery can use lifecycle hooks where available, but a dormant agent cannot be woken by an MCP tool description. Decide delivery and acknowledgment semantics before automatically injecting messages into an agent's context. The current bus requires clients to poll and acknowledge explicitly.
- Consider user-facing review/deletion controls for imported or captured material. Disabling capture stops future writes; it does not remove existing turns, summaries, or backups.

## Known integration caveats

- OMP 18.4.4 links a local package into its **user-level** plugin store even with `--scope project`; uninstall on this machine requires `bun` on `PATH`. Prefer `omp --extension /path/to/setauket/integrations/omp/extensions/setauket.ts` for a one-session trial. OMP `--no-session` runs are intentionally not captured.
- Claude Code transcripts can lag behind hook events. The plugin uses the event's visible prompt and final reply instead of reading the transcript at Stop. A project that already has a Setauket `.mcp.json` may expose a duplicate MCP connection when the plugin is loaded.
- Zed thread snapshots do not have per-message timestamps; imported turns use the thread update time. Historical imports can become eligible for the next archival sweep immediately. Generated summaries are lossy, and the 2026-10-02 synthetic evaluations showed the 1.7B summarizer drops dates/filenames even on moderate sessions and degenerates to echoing (then truncating at `-n 800`) on long or repetitive content; greedy decoding does not help.
